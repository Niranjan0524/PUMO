## 1. What the project is (PUMO)

**PUMO = Personalized Urban Mobility Optimizer**, a final-year B.Tech major project (BTP). It is a multimodal, personalized route-planning research prototype, tested on a **single-city pilot: Bengaluru, India**.

**Modes in v1:** walking + BMTC bus + Namma Metro. (Cycling is optional. Cab/auto/ride-hailing is out of scope for v1.)

**Each journey is scored on six objectives:**

```
J = [T, C, X, W, E, S]
T = travel time          C = monetary cost        X = transfers
W = walking burden       E = estimated emissions  S = safety-risk score
```

**Personalization:** a user profile is a weight vector over these six objectives. Candidate routes are generated once, normalized, then ranked per profile: `Score(J | w) = Σ wᵢ · zᵢ(J)`.

### The two research gaps this project targets

1. **Personalization after disruption is untested.** Existing papers either personalize or handle dynamic data, but none checks whether personalized routes stay *different* after a mid-journey disruption. PUMO injects the *same* disruption at the *same point* of the trip for every profile, reroutes from the current position/time, and measures divergence (`1 − shared segment ratio`).
2. **Safety is not a first-class objective in multimodal routing.** PUMO builds a composite safety-risk index per road/walking edge from streetlights, flood zones, accident/crime evidence, road design and a night-time effect, and uses it as the 6th objective.

### What YOU are responsible for

**Only the data layer.** Turn messy downloads into one clean, reproducible, frozen snapshot that a separate Python routing engine will consume later. You are *not* building the router unless the human explicitly asks.

Primary deliverables:

- `data/processed/` — clean per-source files, all clipped/flagged to Bengaluru.
- A **road/walking graph** (nodes + directed edges) from OSM.
- **Transit tables** (stops, routes, trips, stop_times, connections, fares) from GTFS.
- **Transfer/access/egress edges** linking transit stops to the walking graph.
- An **edge feature table** (`edge_features`) with time, cost, emissions, safety and dynamic-attribute columns.
- Generated files from Section 9 (emission factors, profiles, traffic multipliers, disruption events).
- `data/INVENTORY.md`, `source_metadata.csv`, and a short `data/DATA_REPORT.md` explaining what was used, skipped, and generated.

## 2. Hard rules (never violate)

1. **Never modify or delete files in `data/raw/`.** Treat it as read-only. If it must be reorganized, *copy* into `data/raw_organized/<source_name>/` and keep the original untouched.
2. **Never fabricate real-world facts.** No made-up crime counts, accident locations, fares, timetables, or emission numbers. If a value is unknown, leave it null/omit the component, or use a clearly labeled synthetic/placeholder.
3. **Provenance on everything.** Every derived column must be traceable to its upstream source(s). Every synthetic record has `source_type = 'SYNTHETIC'` plus `generator_version` and `seed`.
4. **Distinguish four kinds of data** everywhere (in code, tables, docs): `MEASURED` (observed), `DERIVED` (computed from measured), `MODELED` (parameterized estimate), `SYNTHETIC` (generated by us).
5. **Reproducible.** Every processing step is a script in `scripts/` runnable from a clean checkout (`make` target or documented command). No manual notebook-only steps for the final snapshot. Fix random seeds.
6. **Coordinate systems:** store/interchange in **EPSG:4326 (WGS84)**. Do all distance/length/buffer/nearest-neighbor operations in a **metric CRS — EPSG:32643 (UTM zone 43N)**, which suits Bengaluru. Never compute metres in degrees.
7. **Do not commit large raw files to Git.** GitHub rejects files over 100 MB. Keep `data/raw/` and big intermediates in `.gitignore`; commit scripts, metadata, docs, small config/CSVs, and small processed outputs only. Suggest Git LFS / Releases / Zenodo for big files, but don't set it up unless asked.
8. **Log decisions.** Any non-obvious choice (thresholds, CRS, dropped records, join radius) goes in `docs/DECISIONS.md` with date and reason.
9. **Fail loudly on bad data, not silently.** Quarantine bad records to `data/quarantine/` with a reason column rather than dropping quietly.
10. **Don't over-engineer.** This is a student research prototype. Prefer simple, readable, testable code over frameworks.

## 4. Step 0 — Inventory & organize (always do this first)

### 4.1 `scripts/00_inventory.py`

Scan `data/raw/` recursively. For every file/folder, record:

- relative path, size, extension, sha256 checksum
- detected type (see heuristics below)
- for tabular: row count, column names, dtypes, null %, sample rows, whether lat/lon columns exist
- for geospatial: CRS, geometry type, feature count, bounding box, whether bbox overlaps Bengaluru
- for GTFS zips: which required files exist, calendar date range, #stops/#routes/#trips
- for PBF: size, bounding box if readable
- for KML/KMZ/GeoJSON/SHP: layers, feature count, geometry types

Write the result to `data/INVENTORY.md` (human-readable) and `data/inventory.json` (machine-readable).

**Bengaluru sanity bounding box (approximate — verify against the actual boundary):**
lon ≈ 77.35–77.85, lat ≈ 12.75–13.25. Flag any dataset whose coordinates fall far outside this.

### 4.2 Detection heuristics (filenames are unreliable — inspect contents)

| If you see… | Classify as |
| --- | --- |
| `*.osm.pbf` or `*.osm` | OSM road/walking source (Section 6.2) |
| `.zip` containing `stops.txt`, `routes.txt`, `trips.txt`, `stop_times.txt` | GTFS feed. Decide BUS vs METRO from agency name, route names ("Purple/Green Line", "Namma Metro", BMRCL) vs. bus route numbers (e.g. "335E") |
| KML/KMZ/GeoJSON/CSV with many point features + light/lamp/pole/ward columns | Streetlights |
| KML/KMZ/GeoJSON with polygons/points + flood/low-lying/inundation/vulnerable wording | Flood layer |
| CSV/XLSX with accident/fatal/injur/FIR/road-accident columns | Accident data (check if lat/lon exist) |
| CSV/XLSX with crime/IPC/police station/cognizable columns | Crime data (check if lat/lon or station/area exists) |
| CSV/GeoJSON with traffic signal/junction points | Traffic signals |
| CSV with `pm2.5`, `pm10`, `aqi`, station columns | Air quality |
| Boundary polygon (ward/BBMP/admin) | City boundary |
| Anything else | List it as `UNCLASSIFIED` in the inventory and move on |

Copy (never move) recognized files into `data/raw_organized/<source_name>/` using a consistent naming scheme (`osm_southern_zone`, `bmtc_gtfs_tumi`, `bmtc_gtfs_vonter`, `bmrcl_gtfs_vonter`, `opencity_streetlights`, `opencity_flood`, `ogd_accidents`, `ogd_crime`, `ogd_traffic_signals`, `cpcb_aqi`, `bbmp_boundary`, …). ## 6. Per-dataset playbook (what each dataset is and how to process it)

For each: **if present → do this; if absent → see Section 8.**

### 6.1 City boundary
- Use any boundary polygon in `raw/` (BBMP / Bengaluru admin). If none is present but OSM is present, derive the Bengaluru administrative polygon from OSM tags (`boundary=administrative`, name Bengaluru/Bangalore) or from the PBF clip bbox.
- Save as `processed/boundary/city_boundary.gpkg`.
- Create a **buffered** version (2–5 km, default 3 km in `thresholds.yaml`) used for graph extraction so trips near the edge don't hit artificial dead ends.
- Mark every node/edge with `in_city` (inside the unbuffered polygon). Keep buffer features in the graph.

### 6.2 OpenStreetMap — base network (MUST-HAVE for everything)
- Likely a large regional PBF (e.g. the Geofabrik "Southern Zone" extract, hundreds of MB). **Clip to Bengaluru + buffer first** before any heavy processing (e.g. `osmium extract` with the buffered boundary/bbox, or a polygon clip), and save the clipped PBF in `interim/`.
- Extract:
  - highways: primary, secondary, tertiary, residential, service, living_street, unclassified, connectors
  - walking: footway, pedestrian, path, steps, crossings, sidewalks where mapped
  - cycling: cycleway, bicycle-accessible roads (optional)
  - `oneway`, access restrictions, bridges/tunnels
  - `highway=traffic_signals`, `highway=crossing`, `highway=street_lamp` (streetlight fallback)
  - rail/metro station geometry and entrances where mapped
  - parks / leisure / landuse polygons (optional green layer)
- Convert traversable ways to **directed edges**: one-way → one direction only; two-way → two directed edges. Keep `osm_way_id` on every edge for traceability.
- Compute `length_m` in the metric CRS (EPSG:32643).
- `base_speed_kmh` by road class from a lookup in `config/thresholds.yaml` (MODELED; label it so). Walking edges use a walking speed (default 4.8 km/h, tunable).
- Remove/repair edges with `length_m <= 0`. Verify one-way direction matches OSM. Check connectivity — report the largest connected component size and isolated fragments.
- Credit OSM (ODbL license) in `README.md`.

### 6.3 BMTC bus GTFS
- Possible sources (human may have one or both): a TUMI Datahub BMTC feed, and/or an unofficial community feed (Vonter `bmtc-gtfs`, derived from the Namma BMTC app). **Both can be inaccurate or outdated; unofficial feed explicitly warns of inaccurate timetable/stop info and incomplete routes.**
- **Check `calendar.txt` / `calendar_dates.txt` date ranges.** A feed whose service dates have lapsed is unusable for date-specific queries. If one feed is expired and the other is valid, use the valid one as primary; keep the other for cross-checking stops/routes. Record the choice and reason in `DECISIONS.md`.
- Run GTFS validation (e.g. the MobilityData validator output if the human added it, or a basic in-code check) and store warnings under `docs/gtfs_validation/`.
- Load: `stops`, `routes`, `trips`, `stop_times`, `calendar*`, `shapes` (if present), `fare_attributes` / `fare_rules` (if present).
- Build `transit_connection` rows: one per consecutive stop pair on each trip (departure/arrival in seconds after midnight; handle times ≥ 24:00:00 correctly).
- Quality rules: valid lat/lon inside the Bengaluru bbox; `arrival <= departure`; valid service date; otherwise quarantine.
- If `fare_attributes.txt` is missing, leave `fare` null and apply the fallback in Section 8 / 9.5. Do not guess fares.

### 6.4 Namma Metro GTFS
- Likely the unofficial BMRCL GTFS (Vonter `bmrcl-gtfs`). **Intermediate station times are approximated** (modeled from stop spacing, dwell time, train speed) — BMRCL does not publish them. Never claim minute-level accuracy; state this caveat in `DATA_REPORT.md`.
- Treat each station as a transit node; use stop_times for time-dependent metro connections.
- Connect stations to the walking network via entrances (OSM) or nearest walkable node.
- **Metro fares:** if the feed has no usable fares, look for a human-supplied `metro_fares.csv` in `raw/`. If absent, leave metro `fare` null and note it (Section 8). Do not invent a fare table.

### 6.5 Transfers, access and egress (DERIVED — no download needed)
- For each transit stop: snap to the nearest suitable walkable node (keep the real stop coordinate, store `snap_dist_m`).
- For each stop, find walkable nodes within radius R (default **400 m**, tunable 300–500 m) → create ACCESS/EGRESS edges using **actual network walking time**, not straight-line distance.
- For each pair of nearby stops with network walk time ≤ transfer threshold (default 5–7 min, tunable) → create TRANSFER edges.
- Store `transfer_time_sec` and `transfer_distance_m`.
- Flag **isolated stops** (no walking path within threshold) rather than deleting them.

### 6.6 Streetlights → `lighting_coverage`, `lighting_risk`
- Possible inputs: OpenCity Bengaluru streetlight CSV/KML (ward-level and/or zone-wise with lat/lon + light type). **Coverage may be partial** — some wards/zones may have only counts, no coordinates. Use only records with valid coordinates for spatial joins; record how many zones/wards were usable.
- Spatially assign each light to the nearest edge within a buffer (default 25 m, tunable). Compute per edge: `light_count`, `lights_per_100m`, then `lighting_coverage` ∈ [0,1] (normalize; document the method) and `lighting_risk = 1 − lighting_coverage`.
- **Important:** an edge with no mapped lights in a region where the data has no coverage is *unknown*, not *dark*. Record coverage regions (e.g. convex hull / zones with data). For edges outside data coverage, set `lighting_risk = null` and drop that component for those edges (see component_flags), or fall back to OSM `street_lamp` nodes if available — never silently treat missing coverage as "unlit".

### 6.7 Flood layers → `flood_risk`
- Possible inputs: OpenCity flooding locations KML (points/polygons), NRSC/Bhuvan flood/vulnerable-area layers. Check temporal scope; treat as historical risk evidence, not current conditions.
- Spatial join to edges (buffer for points, intersection for polygons). `flood_risk` = normalized evidence near the edge. Preserve source and severity if present.

### 6.8 Accident and crime evidence → `accident_risk`, `crime_risk`
- **First check whether the files contain latitude/longitude** (or a mappable location: ward, police station with known coordinates). Most public OGD tables are **aggregate** (state/city/year), not point-level.
- If point-level or small-area spatial data exists → load into `safety_evidence`, join to edges, normalize, set component.
- If only aggregate → store as **context** in `evidence/` and `DATA_REPORT.md`, but **do not** push it into the per-edge score. Set that component to null for all edges and record it in `component_flags`.
- Never assign aggregate counts to edges by guessing locations.

### 6.9 Traffic signals / road complexity → `road_risk` inputs
- From OGD traffic-light points if present, else OSM `highway=traffic_signals` and `highway=crossing`.
- Derive intersection density / crossing counts near each edge. Combine with road class (and width/lanes/sharp-turn proxies **only if** those tags exist) into a normalized `road_risk`.

### 6.10 Air quality (optional)
- CPCB / Bengaluru environment OGD: station points with timestamped pollutant/AQI.
- Interpolate stations to edges (nearest station or inverse-distance weighting) → `air_quality_value`. Keep separate from emissions to avoid double counting. If absent, skip.

### 6.11 Green areas (optional)
- OSM parks/leisure/landuse polygons → per-edge distance to nearest green polygon. Only needed if the team wants a MODyPer-style comfort objective. If OSM is present, it's cheap — compute it; else skip.

## 7. Safety index construction (Gap 2)

Per road/walking edge `e`, compute available components, each normalized to [0,1] (use min–max or percentile rank; document which, apply consistently):

```
accident_risk(e)  = normalized accident evidence near e      (only if spatial data exists)
crime_risk(e)     = normalized crime evidence near e         (only if spatial data exists)
lighting_risk(e)  = 1 − lighting_coverage(e)
flood_risk(e)     = normalized flood evidence near e
road_risk(e)      = normalized road-design proxy
night_risk(e,t)   = f(time_of_day, lighting_risk(e))         (computed at query time)

safety_risk(e)  = Σ aₖ · component_k(e)       over AVAILABLE components only,
                  with weights renormalized to sum to 1 over the available set
safety_score(e) = 1 − normalize(safety_risk(e))
```

- Weights `a1..a6` live in `config/safety_weights.yaml`. **Start with equal weights as an explicit placeholder** and mark them `PLACEHOLDER — not calibrated`. Do not present any weight as evidence-based.
- **Missing components:** exclude them and renormalize the remaining weights. Store which components contributed in `component_flags` (e.g. a bitmask or JSON string per edge) so the report can state exactly what the score was built from.
- Night effect: implement `night_risk` as a function of `lighting_risk` and a night-time indicator; make the time-of-day boundaries configurable (do not hardcode).
- **This is a research composite index, not an objective measure of real-world safety.** Say this in `DATA_REPORT.md`. Avoid claims like "measures safety".

## 9. Data that must be GENERATED (not downloaded) — and how

Everything here is `MODELED` or `SYNTHETIC`, tagged accordingly, with `generator_version` and a fixed `seed`.

### 9.1 Emission factors (`config/emission_factors.csv`)
- Per-mode factor in g CO₂ per passenger-km (modes: WALK, CYCLE, BUS, METRO, and optionally CAR/AUTO/TWO_WHEELER).
- WALK/CYCLE = 0 operational emissions.
- Columns: `mode, factor_g_per_pkm, source, source_url, year, scope (tailpipe|lifecycle), status`.
- **The human fills `factor` and `source`** from a citable reference. Don't mix tailpipe and lifecycle scopes.
- Route emission = `Σ distance_km(mode segment) × factor(mode)`. This is a relative model, not precise vehicle-level accounting.

### 9.2 User preference profiles (`config/profiles.csv`)
These are project-defined starting points, **not observed preferences**:

| profile_id | time | cost | transfers | walking | emissions | safety |
| --- | --- | --- | --- | --- | --- | --- |
| time_focused | 0.40 | 0.10 | 0.10 | 0.10 | 0.05 | 0.25 |
| budget_focused | 0.10 | 0.40 | 0.10 | 0.10 | 0.05 | 0.25 |
| safety_focused | 0.10 | 0.05 | 0.05 | 0.10 | 0.05 | 0.65 |
| eco_focused | 0.15 | 0.10 | 0.05 | 0.10 | 0.50 | 0.10 |
| balanced | 0.20 | 0.15 | 0.10 | 0.10 | 0.15 | 0.30 |

Rows must sum to 1.0 (add a test). Note: time/budget/balanced all give safety 0.25–0.30, so profiles may collapse onto one route — add a sensitivity note rather than changing the weights silently.

### 9.3 Traffic / congestion multiplier (MODELED)
```
dynamic_time_sec(edge, t) = base_time_sec(edge) × traffic_multiplier(edge_class, time_of_day)
```
- Example parameter ranges (project parameters, **not measured Bengaluru facts**): morning peak 1.2–2.0, off-peak 1.0–1.2, evening peak 1.2–2.0.
- Store in `config/traffic_multipliers.csv` keyed by road class and time band; keep `base_time_sec` separate from the multiplier so a real traffic source can replace it later without changing the graph API.
- Walking edges: multiplier 1.0 (unless a rain event changes it, 9.6).

### 9.4 Disruption events (SYNTHETIC) — the core dataset for Gap 1
Generate a reproducible `disruption_event` table. Event types and effects:

| event_type | Representation | Effect |
| --- | --- | --- |
| ROAD_CLOSURE | selected edge + time interval | `closure_flag = true` (edge unavailable) |
| BUS_DELAY | selected trip/segment, +5 / +10 / +20 min | arrival/departure shifted |
| METRO_DELAY | selected metro trip/segment | connection time increased |
| FLOOD | flood-prone edge activated | edge blocked or penalized |
| LIGHTING_OUTAGE | normally lit edge, lighting availability = 0 | night safety penalty increases |
| ACCIDENT | road edge | time penalty or closure + safety penalty |
| TRAFFIC_SPIKE | selected edges | travel-time multiplied |

Generator rules:
- Prefer edges/trips that lie **on a baseline route** so the event occurs mid-journey.
- Don't always pick the shortest-path edge; sample across arterial, residential and transit-rich areas.
- For transit events, pick a stop/segment **after** the trip has begun; record the exact activation point.
- Validate: `start < end`, affected edge/trip IDs exist, otherwise reject.
- Every row: `source_type='SYNTHETIC'`, `generator_version`, `seed`.
- The experiment applies the **identical** event to every profile for the same origin–destination pair.
- If no routing baseline exists yet, generate a generic event pool across the graph now and a route-aware selector later.

### 9.5 Pedestrian density (OPTIONAL, SYNTHETIC)
Only if the safety layer wants it and no real source exists:
```
ped_density(edge, time) = base_density(edge) × land_use_factor × time_of_day_factor
```
Inputs from OSM land-use/POIs (transit station proximity, commercial, school/college, hospital, market, residential, office). Store as `ped_density` with `source_type='SYNTHETIC'`. Skippable.

### 9.6 Weather/rain (OPTIONAL, SYNTHETIC)
A rain event = `rain_intensity` parameter that increases walking time and/or flood-risk/affected-edge cost by a **documented rule**. Only create if asked.

### 9.7 Fare fallback (only if the human asks for a placeholder)
Additive per-mode fare: `journey_cost = bus_fare + metro_fare + other_paid + optional_transfer`; walking = 0. Fares should come from GTFS or a human-supplied, timestamped table. If using a placeholder, mark `PLACEHOLDER`.

## 11. Build order (what to do when the human says "arrange and build")

1. `00_inventory` → `data/INVENTORY.md`. Print found/missing/unclassified.
2. `01_organize` → `raw_organized/` + `source_metadata.csv`.
3. `02_boundary` → boundary + buffered boundary.
4. `03_build_graph` → clip OSM, build directed nodes/edges, base time, connectivity report.
5. `04_load_gtfs` → BMTC and metro tables, validation warnings, quarantine bad records.
6. `05_transfers` → snap stops, ACCESS/EGRESS/TRANSFER edges.

Each step: runnable alone, idempotent, logs what it read and wrote, fails with a clear message if its inputs are missing (and, for non-blockers, **skips with a warning instead of crashing the whole pipeline**).

**Definition of done for the data layer:** one frozen Bengaluru snapshot with (at minimum) the OSM-derived directed graph and `edge_features`; whichever transit and evidence layers were available; one synthetic disruption table; `profiles.csv`; a DATA_REPORT stating exactly what each score was built from; passing tests.

## 12. Downstream context (so your design choices fit later work)

A separate Python routing engine will later:
- run Dijkstra/A* (or k-shortest-paths) on walking/road legs and a RAPTOR-style round-based search on bus/metro, joined by transfer points;
- generate a pool of feasible multimodal candidates, compute `J = [T,C,X,W,E,S]`, normalize, apply a Pareto filter, then rank per profile;
- track journey state (current node/stop, time, mode, completed legs), inject a disruption, update only affected dynamic attributes, reroute from the current state, and compare before/after.

**Primary experiment metric:** route divergence = `1 − shared route-segment ratio` between profiles' selected routes. Secondary: ranking stability, additional travel time, preference preservation, rerouting latency, profile sensitivity; and changes in time/cost/walking/transfers/emissions/safety.

Therefore: keep **edge IDs stable**, keep **static vs dynamic attributes separate**, keep **per-component safety columns** (so score components can be shown), and keep **provenance flags** (so the report can separate real from synthetic).

## 13. Things to be honest about in outputs and docs

- OSM-derived speeds are modeled by road class, not measured.
- Metro intermediate stop times are approximated; bus feeds are unofficial/may be outdated.
- Traffic multipliers, profile weights, safety weights, and synthetic disruptions are project parameters, not observed facts.
- The safety score is a composite proxy built only from available layers; its components differ across the city (`component_flags`).
- Aggregate crime/accident data is not used for per-edge scoring.
- Fares and emission factors are only as good as the sources the human supplies.
